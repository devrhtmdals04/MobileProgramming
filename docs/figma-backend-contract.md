# Figma 기준 백엔드 연결 점검

앱 이름은 그루(GRU)다. 이 문서는 Figma의 화면 **데이터·동작**과 현재 백엔드의 차이를 정리한다.
화면 구현·디자인 토큰·Compose ViewModel/Route 추가는 이번 작업 범위가 아니다.

2026-11-11 기존 파일을 로그인된 Chrome에서 직접 열고 아래 7개 프레임을 확인했다.
Figma 전용 디자인 조회 도구는 이 대화에 노출되지 않아 브라우저의 프레임 선택·렌더링으로
확인했다. 실제 화면의 레이블과 기존 Repository/모델을 대조했으며 숨겨진 동작이나
표시되지 않은 입력 폼은 추측해 확정하지 않았다. Figma 파일은 수정하지 않았다.

## 현재 연결 가능 여부

| 화면/동작 | 실제 화면에서 확인한 요구 | 현재 백엔드 | 준비 상태 |
|---|---|---|---|
| 이메일 로그인 | 학교 이메일·비밀번호·로그인 유지 선택·비밀번호 찾기 | 가입/로그인/로그아웃·세션 복원·재설정 요청 구현. 유지 선택·학교 인증 정책은 없음 | 핵심 인증/재설정 가능, 부가 정책 필요 |
| 피드 | 학교, 사용자 이름, 모임 유형, 모집 상태/마감, 카드 이미지·태그, 찜·관심 수, 정렬 | 사용자 displayName 제공. ClubRepository는 Mock 목록, Promotion은 id/clubId/title/body만 제공 | 실제 피드 데이터 계약 미완료 |
| 탐색 | 이름/관심 분야 검색, 중앙/과·단과대/소모임 구분, 분야·모집 중·초보 가능 필터, 인원·정기 모임·관련도 | 이름/소개 검색·기존 문화/학술/운동 필터만 있음 | 분류 축·필터·카드 필드 보완 필요 |
| 홍보 상세 | 여러 사진, 게시 시각, 모집 일정/대상/인원·모임 장소/시간·회비·가입 과정, 조회·찜·댓글 | 단순 본문·recruitment 문자열. 실제 상세 조회 구현 없음 | 상세 DTO·조회·권한 계약 필요 |
| 관리자 문의 | 메시지·시각·참여자 전용 접근, 동아리 이름·모집 제목/마감, 관리자 표시 이름·응답 안내 | 실제 송수신·권한·재시도 및 getRoomContext 조회 구현 | 공개 정보 게시 후 헤더 연결 가능 |
| 가입 신청 | 이름·학과·학년·연락처, 경험·지원 동기·장비 선택·정기 모임 안내·필수 동의·임시저장 | applyToClub(clubId, introduction) 계약뿐이며 원격 구현 없음 | 입력 DTO·조회/저장·권한 미완료 |
| 수요조사 | 설문 목록·필터·참여하기·응답순 정렬, 개설 의향/원하는 활동 의견 진입 | ClubRequest의 이름/목적/운영 검토 계약만 있음 | 기존 개설 요청과 다른 기능. 범위 결정 필요 |

따라서 **기존 인증·채팅 핵심 백엔드는 활용 가능하지만, Figma 전체를 지원할 준비가 끝난 상태는 아니다.**

## 확정할 백엔드 계약

### 인증·프로필 — 고승민

- 로그인 유지 체크를 해제했을 때 세션 정책을 정의한다. 현재는 Firebase 세션과 명시적 로그아웃 표시를 사용한다.
- 비밀번호 찾기는 [재설정 백엔드 계약](auth-password-reset-contract.md)의 requestPasswordReset(email)을 제공한다. 형식 검증·중립 결과·세션 보존과 실제 Emulator 코드 변경을 검증했다. 화면 연결은 프론트 담당이다.
- 학교 이메일이라는 안내만으로 학교 인증이 구현된 것은 아니다. 허용 학교/도메인과 이메일 확인·접근 시점을 먼저 정해야 한다.
- 가입 신청의 사전 채움에 학과·학년·연락처를 사용할지, 신청 문서에만 받을지 정한다. 현재 User는 id/displayName/role만 있다.

### 채팅 — 고승민, 동아리 정보 필드는 김민성과 합의

- 송수신·서버 시각·참여자 전용 접근·중복 전송 방지·로그아웃 처리는 구현/검증했다.
- 문의 헤더는 [공개 정보 계약](chat-public-context-contract.md)의 getRoomContext(roomId)로 조회한다. 모집 제목/마감과 공개 연락 문서는 선택값이며 운영 게시가 필요하다.
- `users/{adminId}`의 사적 프로필 읽기 권한을 열어 이름을 가져오는 방식은 사용하지 않는다. 현재 users는 본인만 읽는다. 공개 연락 담당 정보와 사적 사용자 정보는 구분해 계약을 정한다.
- 원본 입력 카운터는 1000자, 현재 서버·Repository 한도는 2000자다. UI의 더 작은 한도와 전송은 호환되지만 공통 정책 확정이 필요하다.
- 날짜 구분·시각 표시는 기존 createdAtMillis로 가능하다. 별도 날짜 문자열을 DB에 중복 저장할 필요는 없다.

### 동아리·홍보·탐색 — 김민성

- 모임 유형(중앙/과·단과대/소모임)과 관심 분야(사진·영상 등)는 다른 분류 축이다. 현재 category 하나로 합쳐 취급하지 않는다.
- 조회 모델 후보: 모임 유형·학교, 대표/상세 이미지 참조, 태그, 초보 가능 여부, 인원, 정기 모임, 모집 시작·마감/상시 모집 여부, 모집 대상·회비·장소·가입 과정.
- D-day·갤러리 장수는 날짜·이미지 배열에서 계산할 수 있다. 화면의 예시 숫자를 실제 집계값처럼 저장하거나 반환하지 않는다.
- 추천순·관련도순·응답순이라는 레이블은 정렬 정책을 확정한 증거가 아니다. 지원 정렬과 fallback을 명시해야 한다.
- 이미지 조회용 URL/참조와 사용자의 이미지 업로드 기능은 별개다. 기존 보류된 Cloud Storage 업로드까지 자동으로 도입하지 않는다.

### 가입 신청 — 김민성, 사용자 사전 채움은 고승민과 합의

- 확인한 필드: 이름·학과·학년·연락처, 사진 경험, 지원 동기, 사용할 카메라, 필수 동의. 정기 모임 참여 가능 문구도 보이지만 선택 입력인지 안내인지는 동작 확인이 필요하다.
- 지원 동기는 화면에 최소 30자·최대 500자로 표시된다. 현재 introduction 계약/설계의 1~1000자와 다르다.
- `introduction` 문자열에 전체 폼을 직렬화해 밀어 넣지 말고 타입을 가진 제출 DTO를 정해야 한다.
- 동아리별 질문인지 공통 고정 질문인지, 선택값 enum, 필수/선택 필드와 개인정보 동의 버전/시각을 확정한다.
- 원본은 작성 내용을 관리자에게 전달한다고 설명한다. 신청자 본인과 **해당 동아리 관리자**의 신청 조회 권한을 함께 설계한다. 다른 관리자·일반 사용자는 접근할 수 없어야 한다.
- 원본의 임시저장이 로컬인지 서버/다중 기기용인지 아직 확인되지 않았다. 후자라면 제출과 별도의 draft 계약이 필요하다.
- 화면에 모집 종료 후 30일 내 파기 문구가 있다. 실제 보존·삭제 정책은 확정되지 않았고 자동 삭제도 구현하지 않았다. 문구를 실제 동작 완료로 취급하지 않는다.

### 범위 결정을 먼저 해야 하는 기능 — 공동

현재 개발 계획은 수요조사를 개설 요청으로 해석하고 별도 설문 서비스·댓글·알림·추천 알고리즘을 제외했다.
실제 디자인에는 설문 참여, 댓글 입력·답글, 찜한 모임 탭/북마크, 관심 수, 알림 진입이 보인다.
원본을 읽었다는 이유만으로 기존 MVP를 변경하거나 이 기능들의 완료를 선언하지 않는다.

특히 `clubRequests`와 설문/설문 응답은 목적·상태·권한이 다르다. 설문을 포함한다면
독립 계약과 중복 응답·집계·작성자 권한 정책이 필요하다. 확인한 설문 화면은 목록이므로
실제 응답 폼의 질문·입력 타입까지 확인한 것은 아니다. 개설 요청 메서드에 임의로 대응시키지 않는다.

## 다음 구현 순서

1. 공동: 설문·댓글·찜·학교 인증·임시저장의 MVP 포함 여부와 정책 확정.
2. 고승민: 인증 보완과 채팅 헤더의 공개 정보 읽기 계약을 정리. 기존 송수신 계약은 활용.
3. 김민성: 동아리/홍보 조회 모델·가입 폼 DTO와 검증 기준 확정.
4. 각 담당: Repository 원격 구현·Rules·인덱스·실패/타인 접근 테스트.
5. 전달: 실제 사용 가능한 메서드·필드·오류·예제 데이터와 미구현 항목을 명시해 프론트에 인계.

최초 점검 후 비밀번호 재설정과 문의 공개 정보 Repository·Rules·테스트를 추가했다. Figma 디자인과 프론트 화면은 변경하지 않았다.
기존 [채팅 UI 연결 안내](chat-ui-handoff.md)는 이전 지원 구현의 기록이다. 앞으로의 담당 범위는
사용자 지시에 따라 백엔드·DB이며 화면·ViewModel·Route 작업은 프론트 담당이다.
