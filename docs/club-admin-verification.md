# 동아리 관리자 확인과 운영자 계정

전화번호 인증은 로그인 수단이다. 동아리 대표자 신분이나 GRU 운영자 권한을 증명하지 않는다.

## 신청과 승인

1. 회원은 탐색의 공식 동아리 상세에서 직책과 사유를 작성해 관리 권한을 신청한다.
2. GRU 운영자는 프로필의 내 동아리 관리에서 대기 신청을 확인한다.
3. 신청자가 제공한 연락처만 신뢰하지 않고, 숭실대학교 동아리연합회 공식 소개에서 독립적으로 찾은 채널로 대표자 여부를 확인한다.
4. 직접 확인한 HTTPS 채널 주소와 검토 기록을 남기고 확인 체크 후 승인한다. 자동 메시지는 전송하지 않는다.
5. 승인 상태와 `clubs/{clubId}.adminId` 연결을 하나의 Firestore 트랜잭션으로 저장한다. 승인된 회원만 소개와 모집 안내를 수정할 수 있다.

신청은 `clubAdminRequests/{clubId}__{uid}`에 저장한다. 본인 내역은 신청자만, 전체 검토 내역은 운영자만 조회한다. 반려 사유를 확인한 뒤 재신청할 수 있다. 이미 관리자가 있는 동아리는 신규 연결을 거절한다. 권한 이전·다중 관리자 기능은 별도 구현 전까지 허용하지 않는다. 운영자 자신의 신청은 다른 운영자가 검토해야 한다.

## 전용 운영자 계정 등록

일반 회원 테스트 계정과 별개로 개발용 가상번호 `+16505550102`를 사용한다. 인증코드는 Firebase Console에서 프로젝트 소유자가 직접 설정하고 Git에 저장하지 않는다. 가상번호 계정은 개발 검증 전용이다. 실제 운영 전에는 소유자가 관리하는 실제 인증 수단으로 교체해야 한다.

1. Firebase Authentication의 전화 제공업체에서 개발 가상번호와 인증코드를 등록한다.
2. 그 번호로 로그인하고 `그루 운영자` 프로필을 생성한다. `DedicatedOperatorConnectionTest`는 명시적인 `operatorConnection=true` 및 런타임 `operatorSmsCode`에 한해 해당 계정을 생성하고 UID를 출력한다. 이 테스트는 권한을 부여하지 않는다.
3. 신뢰할 수 있는 Firebase 프로젝트 소유자가 Console 또는 Admin SDK로 `operators/{전용 계정 UID}` 문서에 boolean `enabled: true`를 등록한다. 앱에서는 이 컬렉션을 생성·수정·삭제·목록 조회할 수 없다. 본인 문서 조회만 허용한다.
4. 운영자 계정으로 다시 로그인하거나 관리 화면을 새로고침하여 검토 영역을 확인한다. 문서의 `enabled`를 false로 설정하면 서버가 다음 검토 작업을 거절한다.

기존 `operator: true` custom claim도 호환하지만 새 전용 계정은 보호된 운영자 명부를 사용한다. 일반 사용자 프로필의 `role`은 운영자 판정에 사용하지 않는다. 클라이언트에서 `role`을 수정하거나 운영자 명부를 작성하는 우회 경로는 없다.

## 공개 데이터와 검증 범위

`clubs`에는 공개할 이름·분류·소개·모집·관리자 UID·공식 출처·수정 시각만 저장한다. 로그인한 회원이 공개 동아리 목록을 조회할 수 있으므로 대표자 전화번호나 비공개 증빙을 넣지 않는다. 공식 목록의 이름과 분류, 출처는 유지하고 승인된 소개·모집·관리자 연결만 병합한다.

Rules 테스트는 권한 상승 차단, 원자적 승인, 자기 승인 차단, 타인 편집 차단, 반려와 재신청, 운영자 회수를 검증한다. Android 통합 테스트의 승인은 로컬 Emulator fixture에만 적용한다. 실제 숭실 동아리 대표자 확인이나 학교의 서비스 승인을 테스트로 대체하지 않는다.

배포 시 이 저장소의 `firestore.rules`도 반드시 함께 반영한다. 이전 규칙에서는 운영자 명부 및 신청 경로가 거절된다.
